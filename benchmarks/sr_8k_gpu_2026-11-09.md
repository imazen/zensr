PyTorch 2.15.0+cu132, CUDA 13.2 and cuDNN 9.26.0. Both full-frame models fit.

## Scope and correctness

All computation is FP32, with TF32 disabled for cuDNN and matmul. Deterministic
algorithms are enabled; cuDNN benchmark/autotuning is disabled. NCHW, batch one,
full-frame eager inference; no tiling, autocast, INT8, compilation or CUDA graphs.

SPANF uses the original NTIRE2025 team24 author architecture. Its checkpoint's
ordered FP32 weights exactly match the retained CPU FP32 artifact. Before
measurement, the mixed f16-weight/f32-bias native artifact is expanded into the
author model, matching the weights used by the native CPU size check. This is
FP32 execution with reduced-precision stored weights, not FP16 computation.
The author source revision is `b69fb668c0362deb696eecbfdebfaa5c2fcdfcb4`;
the two author files are copied unchanged and hashed in the experiment identity.
DSCF uses the same pinned author FP32 checkpoint as the CPU comparison.

Both models receive exactly the CPU experiment's periodic 2048-pixel timing
fixture, SHA-256 `cc41343d9772fb4516d4db4f8f080417478ca01a09a618ac8534e789c832f6d6`.
This is a performance fixture, not a native-resolution quality sample. One
full-size warmup precedes two timed calls. Each produces finite 8192×8192 RGB
and exactly matches its own warmup output hash. GPU hashes differ from the CPU
hashes; cross-backend pixel equivalence and perceptual quality remain unverified.

Inference latency uses synchronized CUDA events. The independent synchronized
host timer agrees, ruling out reporting asynchronous submission time as the
model latency. Device input is already resident. Transfer rows measure separate
pinned copies; they are not an end-to-end pipeline latency measurement. Model
loading, pinned buffer allocation, validation, hashing, codecs, JPEG repair and
IQA are outside the timing. Inference output/scratch allocation is included.

VRAM peaks use `torch.cuda.reset_peak_memory_stats()` before each timed inference,
then `max_memory_allocated()` and `max_memory_reserved()` afterward. They include
model, input, output and PyTorch-managed workspace. Reserved memory includes the
warm caching allocator pool; driver/context memory outside PyTorch is excluded.
Host `/usr/bin/time -v` peak RSS was 3,790,536 KiB for SPANF and 3,785,768 KiB
for DSCF, including pinned buffers, loading and verification. No OOM occurred.

## Evidence and reproduction

Numerical worker/plan source: `065bbe06e7658cfdf97a0a1c3254baea8fa1b89a`.
Zenbench Iterate ran one fresh process per model, one block, two samples and no
A/A clone. CPU placement was confined to performance cores 0–7. No competing
GPU compute process was observed before launch; the GPU was released afterward.
Whole-host cleanliness was not certified. These are exploratory observations,
not a statistical confirmation or a production backend promotion.

```text
run-heavy: done rc=0 9s | peak-RSS 3.61GiB | min-avail 21921MiB | peak-load 1.90
```

On i265, `/mnt/v/output/zensr/sr-8k-gpu-20261109/` retains the plan, source and
checkpoint, identities, raw CUDA-event samples, packet and full worker logs.
The project NAS mirror is `output/zensr/sr-8k-gpu-20261109/`;
`ARCHIVE_VERIFIED-v1.json` binds all archived files and the packet digest.
Existing CPU and DSCF study directories retain the shared input and model assets.
No IQA maps run. Synthetic benchmark outputs are hashed and released in RAM.

Reproduce with `just external-sr-8k-gpu-plan --root <new-root> --cpu-root
<cpu-8k-root> --sr-root <original-sr-root> --external <external-model-root>
--python <sr-venv-python>`, after staging the two author SPANF files under
`<new-root>/spanf/`. Run the retained zenbench binary's
`pair <new-root>/plan.json --output <new-root>/run-v1` inside the recorded P-core
boundary and `run-heavy --mem 12G --jobs 4`, with MemoryMax=12G and
MemorySwapMax=0. Use `just external-sr-8k-gpu-report <new-root>` to verify the
retained assets/logs/packet and extract results. These tools add research
measurement only; no product API, backend or default changes.
