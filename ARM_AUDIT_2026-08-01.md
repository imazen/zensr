# zensr ARM/NEON audit — 2026-08-01

First SIMD measurement this crate has ever had. Apple M4 Pro, aarch64.
`cargo bench -p zensr-micro --features internals --bench kernel_tiers`

## Result: no sub-parity kernels

| kernel | neon | forced scalar | ratio |
|---|---|---|---|
| `silu_dispatch` (1M f32) | 639.4 us | 13254.5 us | **20.7x** |
| `conv3x3_dispatch` (32->32ch, 128x128) | 7.3 ms | 8.2 ms | **1.12x** |

Both above parity, so nothing here is a regression and no code was changed.

**Re-measured 2026-08-01 on THIS tree.** The table above was produced on a
local snapshot that predated the relicense/scrub commit and was never pushed;
this file was replayed onto `main` afterwards, so the measurement was re-run here
rather than carried over on trust:

| kernel | neon | forced scalar | ratio |
|---|---|---|---|
| `silu_dispatch/1M` | 503.9 +-2.6 us | 10203.6 +-747.1 us | **20.25x** |
| `conv3x3_dispatch/32x32x128x128` | 5.8 +-0.4 ms | 6.5 +-0.4 ms | **1.12x** |

**The ratios reproduce; the absolute times do not.** Both arms are faster here
than in the original run, and the re-run happened while another heavy job shared
the box (zenbench flagged 94 of 100 rounds noisy, and the +-747 us spread on the
scalar arm reflects that). Absolute numbers from either run should therefore be
read as box-and-load-specific; the ratio is the durable quantity, and it is the
quantity the conclusion rests on. Nothing about "no sub-parity kernels" changes.

Dispatch audit: all ten `incant!` sites in `src/simd.rs` carry a `neon` arm
(`[v4x(cfg(avx512)), v4(cfg(tier_v4)), v3, neon, wasm128, scalar]`), and the
`#[magetypes(v3, neon, wasm128, scalar)]` layers generate NEON variants. The one
`[v3, scalar]` site is inside `#[cfg(target_arch = "x86_64")]
spanf_x4_simd_force_v3`, an x86-only force helper — not an ARM gap.

## Reading these ratios

NEON is BASELINE on aarch64, so the "scalar" arm is autovectorized too — these
are hand-written-vs-autovectorized, not SIMD-vs-nothing. Ratios are also biased
AGAINST the dispatched arm: the forced-scalar path inlines into the bench loop
while the `#[arcane]` arm carries a target_feature boundary and cannot (measured
at ~8% in zenresize, by pointing both arms at byte-identical source). So ~1.00x
is a PASS and below ~0.95x is the finding.

## The conv3x3 lead — PROFILED, and it does NOT warrant a rewrite

`conv3x3` is the dominant cost of the network and returns only **1.12x** where
`silu` returns 20.7x. That asymmetry looked like the hand-written kernel failing
to exploit something structural. Profiled before touching it, and it is not:

| quantity | value |
|---|---|
| FLOPs per call (32->32ch, 128x128, 9 taps) | 302 MFLOP |
| achieved | 41.4 GFLOP/s |
| vector loads per 4-channel output tile | 288 |
| FMAs per tile | 1152 |
| **load : FMA ratio** | **0.25** |

One load per four FMAs — the kernel is FMA-throughput-bound, not load-bound. The
obvious lever (derive `l`/`m`/`r` from ONE load via lane shifts instead of three
overlapping loads) attacks 288 loads against 1152 FMAs and therefore cannot pay.
And the structural work is already done: `conv3x3_row4` blocks 4 output channels,
uses packed quad-major weights, keeps accumulators register-resident, and runs a
clean FMA chain.

So the 1.12x is LLVM autovectorizing the SCALAR arm well — NEON is baseline on
aarch64 — not a deficient NEON arm. **Do not rewrite this kernel on the strength
of the 1.12x number alone.** A real gain would need a different algorithm
(the Winograd path next to it already exists for that) or multi-row accumulation
to raise arithmetic intensity further, and both need a measurement showing the
current one is actually leaving something on the table. This one does not.
